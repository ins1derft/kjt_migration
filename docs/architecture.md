# Архитектура монорепозитория

Монорепо объединяет публичный фронтенд на Next.js 16 (App Router) и бэкенд на Laravel 12 с админкой MoonShine 4 и PostgreSQL 18. Трафик всегда проходит через Nginx; оркестрация только через `docker/compose.sh`.

## Поток запросов (runtime)
```
Браузер → Nginx (:8080 dev / :80 prod)
  ├─ /admin, /api, /build, /storage, /vendor → php-fpm (backend-php) → PostgreSQL
  └─ остальное (/,_next, статические) → Next.js (frontend)
Next.js при загрузке данных дергает /api/* (через Nginx) → Laravel → PostgreSQL
```

## Фронтенд (директория `frontend/`)
- Next.js 16, App Router, SSR. Стилизация — TailwindCSS (utility `cn` в `src/lib/utils.ts`). Дизайн‑система под новый лендинг: Open Sans + Lorin, палитра brand.sky/orange/gradient start‑mid‑end, `shadow-glow`, `bg-brand-gradient`, новые анимации/токены в `app/globals.css` и `tailwind.config.js`. Safelist в `tailwind.config.js` генерирует `pt-[0..600px]`/`pb-[0..600px]` под произвольные паддинги из CMS.
- Главные маршруты:
- `/` (`app/page.tsx`) — лендинг теперь тоже приходит из сущности Pages: сервер тянет `/api/pages/home` и рендерит блоки через общий реестр. Если `type=product_landing` и в блоках нет `product_hero`, перед блоками добавляется ProductHero из связанного продукта. Формы подтягиваются только из `product.form` и блоков `product_hero` (`formsByCode`). При отсутствии записи slug `home` выводится мягкий плейсхолдер для админа. Данные для существующего лендинга миграцией `2025_12_03_000100_seed_home_page_from_static` автоматически создают опубликованную страницу `slug=home` с теми же блоками, что были в статике.
- `(marketing)/[slug]` — либо продуктовые лендинги (`type=product_landing`), либо статические страницы (`type=static`), данные с `/api/pages/{slug}`, блоковый рендер через реестр. Для `product_landing` дополнительно прилетает `product`, `variants`; перед блоками жестко рендерится `ProductHero` из продукта **только если** в блоках нет layout `product_hero` (чтобы избежать дубляжа). Конфиги форм подтягиваются на сервере для всех кодов, встреченных в продукте и в блоках `product_hero` (map `formsByCode` → передается в рендерер); QuoteModal работает без клиентского GET. Новый layout `product_hero` позволяет заполнить поля вручную и не опираться на Products API (`useProductData=false`), выбирать вариант бейджей (`badgeVariant=image|card`), задавать только изображения + подпись (без icon key); CTA показывается при наличии `formCode`, даже если страница статичная и продукта нет; если `useProductData=true` и продукта нет, CTA скрывается. При желании можно оставить автозаполнение из `product` (`useProductData=true`). Games блоки берут игры из сущности `Game` (авто — все/limit, ручной — выбранные slug’и из выпадающего списка).
  - `/news` и `/news/[...slug]` — список статей `type=news` и детальная статья по slug последнего сегмента.
  - `/case-studies` — список `type=case_study`, карточки ведут на `/news/{slug}`.
  - `/games` и `/games/[slug]` — каталог игр и детали.
- `/store` и `/store/[slug]` — каталог и карточка StoreProduct.
- `/case-studies` — список кейсов (articles type=case_study) на Tailwind/shadcn `Card`.
- Конфиг: `next.config.mjs` (`output: "standalone"`). В dev переписывает `/api/*` на `http://nginx/api/*` или `NEXT_API_PROXY`; в прод переписываний нет.
- Глобальный каркас `app/layout.tsx` выводит шапку/футер (`src/components/layout/SiteHeader|SiteFooter`), поднимает меню `header`/`footer` из `/api/menus` (helpers `src/lib/menus.ts`, revalidate 300s) **и единый объект настроек сайта** из `GET /api/site-settings` (`getSiteSettings` в `src/lib/api.ts`). Header — двухуровневый sticky (40px синий топ-бар + 60px белый основной), контейнеры `max-w-[1189px]` (2xl `1320px`, без внутренних паддингов на 2xl) с центральным слотом под логотип 110×100; нижний ряд — сетка `1fr/auto/1fr` с адаптивными зазорами: `48/80/120px` слева и `50/80/95px` справа (переключение на мобильный режим при ширине <1000px). Mega‑menu рендерится для первого пункта с `children` (по данным API), привязки к тексту нет. Мобильный дровер: стрелка показывается только у пунктов с вложениями; иерархия дочерних пунктов выводится двумя уровнями (группа → элементы). Footer — рефреш из дизайн-системы: column “Helpful links” и остальные навигационные ссылки по‑прежнему берутся из меню `footer`, а соцссылки, общие контакты (`contact_*`) и поддержка (`support_*`, телефоны/почта) теперь приходят из сущности настроек сайта. Палитра/градиенты задаются в `globals.css`.
- SEO-база: переехали на `next-seo` + `next-sitemap`. `src/lib/seo.ts` конвертирует конфиг `next-seo.config.ts` (titleTemplate, OG/Twitter, canonical из `NEXT_PUBLIC_SITE_URL`) в `Metadata`; `DefaultSeo` подключён в `app/layout.tsx`. Динамические страницы собирают `Metadata` через `mergeSeo`/`nextSeoToMetadata`. JSON-LD остаётся для статей (NewsArticle), игр (VideoGame) и товаров магазина (Product). robots/sitemap теперь генерируются postbuild через `next-sitemap` (конфиг `next-sitemap.config.js` с выборкой статичных путей + articles/games(is_indexable)/store products из API); статические файлы лежат в `public/` после билда, отдельные маршруты `app/robots.ts`/`app/sitemap.ts` удалены. Стили — брендовые HSL-токены в `app/globals.css`, Tailwind config `tailwind.config.js`, postcss конфиг `postcss.config.js`.
- Переменные окружения, доступные клиенту: `NEXT_PUBLIC_API_URL` (по умолчанию `http://localhost:8080/api`; в прод‑компоузе прокидываем `http://nginx/api`, чтобы SSR ходил к Laravel через Nginx внутри сети compose), `NEXT_PUBLIC_SITE_URL` (для `next-seo`/`next-sitemap`; fallback `https://kidsjumptech.com`), опционально `SITEMAP_API_BASE` для генерации sitemap.
- Оптимизация медиа: `resolveMediaUrl` строит абсолютные ссылки для Next Image через `NEXT_IMAGE_BASE_URL` (dev: `http://nginx`, внутренний хост в сети compose; fallback — `NEXT_PUBLIC_SITE_URL`). В блоке `hospital_equipment` все изображения (иконки фич, фон CTA, футерный значок) рендерятся через `next/image` с `unoptimized` и `resolveMediaUrl`, чтобы сохранить контроль размеров/overlay и избежать ошибок `_next/image` при временной недоступности файлов. Анимация градиента теперь включается только по hover через класс `animate-gradient-hover` (utility в `app/globals.css`) на кнопках с градиентным фоном.
- Блоковый рендерер: типы → `src/lib/blocks/types.ts` (перенесены из прежнего design), реестр `src/lib/blocks/registry.tsx` рендерит блоки новым набором дизайн-компонентов (Hero, HeroValueGrid, FeatureGrid, ProductHero, ProductCarousel, GamesGallery, **GamesGrid**, News, Stats, FAQ, WhyUs, ProductDescription, ProductNav, OurApproach, ProductSpecs, CompareModels, CTASection, **DiscountBanner**, HighlightCTA, Reviews, TrustedBy) из `src/components/blocks`. При рендере каждый блок оборачивается в `div id=<anchor>` с автогенерацией якоря: приоритет `values.anchor` → пресет по имени лэйаута (hero/description/specs/compare/approach/faq/cta/etc) → slug заголовка → slug имени лэйаута; slugifier транслитерирует кириллицу и чистит не‑ASCII, дубликаты получают суффиксы `-2`, `-3`. Формат данных API прежний `{ name, key, values }`, маппинг на новый дизайн идёт по `name`. Legacy/shadcn блоки удалены; поддерживаются только текущие компоненты. В админке для всех layout одно текстовое поле `padding` (строка с классами/inline-стилями Tailwind) + опциональный `backgroundColor` (Color picker с HEX) для переопределения фона; при пустом значении фон берётся из дефолтного класса компонента. Числовых `padding.top/bottom` больше нет.
- Новый layout `potential_uses` (frontend `PotentialUses`) для страницы `hospital-equipment`: белый верх с заголовком 64px (38px на 360px), `font-heading` 700, `leading-1.05`; таб-группа с закруглением 100px и тенью `0 1px 10px rgba(0,0,0,0.05)` у активной кнопки, текст табов #4f5459. Габариты таб-бара: 954×87 на 1920, 954×87 на 1189, 320×97 на 360 (две строки по 2 таба; отступ до карточек 50px/50px/74px). Тайтлы карточек `font-heading` extraBold, 24px (16px мобайл), цвет **#4571ff** (токена нет); описания `font-sans` 20px (16px мобайл) `leading-1.4`, цвет `text-brand-dark/70`. Дефолтные изображения лежат в `frontend/public/images/hospital-equipment/potential-floor.jpg` и `potential-table.jpg` (путь в данных начинается с `/images/...`). Миграция `2025_12_07_000400_seed_potential_uses_block` добавляет блок первым на страницу `slug=hospital-equipment`.

## Бэкенд Laravel (директория `backend/`)
- Вход: `public/index.php`; API и админка обслуживаются через Nginx.
- Основные маршруты (`routes/api.php`):
  - `GET /api/health` → `{ ok: true }`
  - `GET /api/menus?location=header|footer` — активные меню с вложенными пунктами (`label`, `url`, `slot`, `icon`, `opens_in_new_tab`, `children`).
  - `GET /api/site-settings` — singleton-настройки сайта (`logo_url`, `header_phone`, `header_whatsapp`, `contact_*`, `support_*`, `social_links[{label,href,icon,targetBlank,color,headerColor,footerColor}]`); используется шапкой и футером как единственный источник логотипа, контактов и соцсетей. Если запись ещё не создана, эндпоинт возвращает `404` без каких-либо дефолтов — сначала заведите данные через MoonShine. `icon` поддерживает Iconify ID (`set:name`, например `mdi:facebook` или `streamline:facebook`); `color` сохраняется для совместимости и применяется по умолчанию, `headerColor`/`footerColor` позволяют задать отдельные HEX-значения (`#RRGGBB`) для шапки и футера.
  - Контентные страницы: `GET /api/pages/{slug}` — только `status=published`, ответ `PageResource` (`slug`, `title`, `type`, `seo{title,description,canonical,og_image}`, `blocks[{name,key,values}]`); API не перекладывает их в `layout/fields`, фронт сам мапит `name→layout`, `values→fields` при рендере.
  - Статьи: `GET /api/articles?type&category&limit&page`, `GET /api/articles/{slug}` — только опубликованные; `ArticleResource` включает SEO и категории.
  - Игры: `GET /api/games?limit`, `GET /api/games/{slug}` (`GameResource`, категории, products_used, game_type, video_id, video_url, is_indexable).
  - Продукты-лендинги: `GET /api/products?limit`, `GET /api/products/{slug}` (`ProductResource` с variants и связанной form для CTA).
  - Магазин: `GET /api/store/products?limit&available`, `GET /api/store/products/{slug}` (`StoreProductResource` с категориями, доступностью, specs).
  - Отзывы: `GET /api/reviews?limit&fields&filter[ids]=1,2&filter[is_active]=true` — по умолчанию только активные, сортировка `position` → `review_date` → `id`; отдаёт name/date/rating/text/avatar/source_url/position/is_active.
  - Формы: `GET /api/forms/{code}` — возвращает `code`, `title`, `topic`, `submit_label`, `success_message`, `fields[]` (name/label/type/options/required); `POST /api/forms/{code}` — принимает `topic` (из запроса или из формы), валидирует обязательные поля (email + required из `forms.config`), создаёт `Lead` с `topic`, `payload`, `source_url`, `utm`, `submitted_at` (timestamp сервера), ответ `{ success: true }` 201.
- Веб-роут `/` (стандартный `welcome`), остальное закрыто MoonShine.

### MoonShine (админка)
- Провайдер `App\Providers\MoonShineServiceProvider` регистрирует все ресурсы; layout `App\MoonShine\Layouts\MoonShineLayout` (палитра Purple, кастомное меню). В `App\Providers\AppServiceProvider` вручную регистрируем `MoonShine\TinyMce\Providers\TinyMceServiceProvider`, т.к. auto-discovery его не подтягивает и без него падают TinyMCE-поля в админке.
- Адрес админки: `/admin` (prefix из `config/moonshine.php`), аутентификация `moonshine` guard.
- Ресурсы (CRUD):
  - **Контент:** `PageResource` (конструктор блоков: hero, features_grid, games_list, news_list, quote_form), `ArticleResource` (типы: news/case_study/blog/in_press, категории m2m), `ArticleCategoryResource` (иерархия категорий).
  - **Игры:** `GameResource` (genre/target_age, hero_image, m2m категории), `GameCategoryResource`.
  - **Продукты:** `ProductResource` (rating/review_count_label, badges json, form belongsTo Form; без SEO-полей) и `ProductVariantResource` (image upload `products/variants`, price/label/position). Атрибуты варианта редактируются четырьмя `RelationRepeater` (кастом `RelationRepeaterWithMutators`, чтобы апдейты гонялись через модельные мутаторы): отдельно для `string/number/boolean/json`, каждый жестко фильтрует `ProductAttribute` по типу (в `valuesQuery`) и пишет FK в колонку `product_attribute_id`; колонка Type выводится как read-only текст с дефолтом соответствующего блока, сразу видна при добавлении и уходит в форму. Значение хранится в колонке `value` (jsonb), но для json-типа форма теперь читает/пишет через аксессор `value_json` (список `{key,value}`); мутаторы кодируют нормализованный массив в JSON-строку перед сохранением, чтобы каст `json` не пытался декодировать уже готовый массив. Для сохранения используется свежий relation‑builder на каждую строку (после очистки лишних записей), чтобы не оставались `whereNotIn` из шага удаления и апдейты существующих значений проходили через мутаторы/касты.
    - string → сохраняется как JSON-строка (json_encode),
    - number → число,
    - boolean → bool,
    - json → объект, собранный из key/value.
    Тип определяется по `attribute_type`. Серверная валидация `exists ... where type=?` не даёт выбрать чужой тип. `ProductAttributeResource` управляет справочником атрибутов, `ProductVariantAttributeValueResource` — значениями; превью `image` выводится с диска `public/products/variants`.

  - В списке Pages добавлен MoonShine-фильтр Select по `type` (`product_landing`/`static`), чтобы быстро разделять лендинги продуктов и статические страницы.
  - В списке Pages в выпадающем меню строк добавлен Clone: модалка с полями Title/Slug (предзаполнены `<title> (copy)` и `<slug>-copy` с авто-уникализацией). Копирует всю страницу вместе с блоками/SEO/связями и создаёт новый `Page` со статусом `draft` и пустым `published_at`, после сохранения редиректит на форму редактирования.

  - **Формы и лиды:** `FormResource` (topic, JSON-конфиг форм: submit_label, success_message, поля с типами text/email/phone/textarea/select/checkbox), `LeadResource` (topic, payload, utm JSON; деталь выводит payload/utm таблицей key→value плюс source_url, submitted_at и связанный product_variant; в списке лидов включён мультивыбор с массовым удалением как в остальных ресурсах).
- **Отзывы:** `ReviewResource` (name, review_date, rating 1–5, текст TinyMCE, аватар upload в `storage/app/public/reviews` с валидацией `image|max:5MB`, source_url, position, active).

Индекс Menu Items теперь дерево с drag-and-drop сортировкой (MoonShine Tree Resource) и принудительной фильтрацией по выбранному меню; в форме Parent выбирается из элементов текущего меню. Штатные фильтры MoonShine не работают с TreeComponent, поэтому на странице дерева есть собственный OffCanvas-фильтр (кнопка Filters в топ-баре) с полями menu/slot/parent; `MenuItemResource::modifyQueryBuilder` вручную применяет `filters[menu|slot|parent]` и подставляет первый доступный `menu_id` по умолчанию.

Для соцсетей можно задать Iconify ID и отдельные HEX-цвета для шапки и футера (`header_color`, `footer_color`), либо оставить пусто, чтобы применялся общий цвет/градиент; поля цветов редактируются через встроенный color picker MoonShine (`Color` field).

- **Деревья с drag-and-drop:** `ArticleCategoryResource`, `StoreCategoryResource` и `MenuItemResource` переведены на `lee-to/moonshine-tree-resource` (MoonShine v4). Индекс-страницы теперь рисуют дерево с сортировкой перетаскиванием и автоматическим сохранением `position`; массовое удаление отключено. Меню-дерево всегда фильтруется по выбранному меню (по умолчанию первый), новые узлы получают позицию в конце ветки, поле `Position` из формы меню убрано.
- В `PageFormPage` у конструктора блоков включён кастомный `onApply` для `Layouts`, чтобы MoonShine сохраняла dot-ключи вложенных полей (`padding`, `query.*`) из `blocks[...]` как есть; ранее они затирались пустыми строками при сохранении. Поле `padding` теперь одно строковое (класс/стили Tailwind); пустое значение оставляет дефолтные отступы блока. Аккордеоны Layouts рендерятся через кастомный оверрайд `moonshine-layouts-field/layout` с `persist=false`/`open=false`, поэтому блоки всегда загружаются свёрнутыми и не запоминают открытое состояние (ручное раскрытие остаётся штатным, валидация продолжает раскрывать нужный блок через `collapse-open`).
- Все CRUD-страницы используют валидации уникальности slug/code и базовые required-правила; загрузки файлов ведутся на диск `public` в подкаталоги `seo/`, `pages/hero`, `articles`, `games`, `products`, `store`.

- **Оркестрация:** `docker/compose.sh <environment> …` (обязательное использование). Композ-файлы: `docker/development.compose.yml`, `docker/production.compose.yml`. Env-файлы: `.env.development`, `.env.production`.
- **Сервисы (dev):**
  - `frontend`: Next dev server на 3000, код смонтирован.

Лимит памяти PHP в dev поднят до `512M` через `php.dev.ini` → `/usr/local/etc/php/conf.d/php-memory.ini`; лимит количества одновременных файловых полей (`max_file_uploads`) увеличен до `150`, чтобы MoonShine формы с большим числом иконок/галерей сохранялись без ошибки "Maximum number of allowable file uploads has been exceeded".

Лимит памяти PHP в prod выставлен на `256M` через `php.prod.ini` → `/usr/local/etc/php/conf.d/php-memory.ini`; параметр `max_file_uploads` увеличен до `150` по той же причине, что и в dev (массовые аплоады в MoonShine).
  - В `nginx.prod.conf` `/storage/` настроен через `alias` на `storage/app/public` (без проксирования в PHP) с CORS `Access-Control-Allow-Origin: *`.

- Формы: структура хранится в `forms.config`, отправленные данные валидируются на бэкенде, сохраняются в `leads.topic` + `leads.payload`/`utm`; связь по `form_code`. `topic` берётся из запроса (например, название блока в InteractiveShowcase) либо из самой формы, и также пробрасывается в payload, если не было явного поля `topic`. Конфиг формы фронт получает на сервере Next через `GET /api/forms/{code}` (не виден в DevTools пользователя) и передает поля в клиентскую часть; в браузере выполняется только `POST /api/forms/{code}`. В админке MoonShine payload/utm показываются как таблицы key→value на детальной странице лида. Конфиг может включать `topic`, `submit_label` и `success_message` для текста кнопки/ответа.

- Повторяемые JSON-поля в админке (конфиг форм, спецификации варианта, бейджи продукта, списки/фильтры блоков страницы и их вложенные коллекции) теперь рендерятся в стандартной табличной форме (горизонтально). Это убирает падение PHP 8.3 `ComponentSlot::__toString()` на PageFormPage, которое возникало из-за передачи UI-компонентов в слот при вертикальном режиме. Дополнительно, в layout `interactive_header` мы убрали `Image::multiple()` внутри Json (fixed `icon1..3`) — MoonShine сейчас не умеет рендерить `Components` коллекции в ячейке Json-таблицы, поэтому multi-upload приводил к той же ошибке.
- ProductHero на `product_landing` берет `form.code` из `Product.form` и открывает клиентский QuoteModal: конфиг формы (`/api/forms/{code}`) подтягивается на сервере Next в `(marketing)/[slug]/page.tsx` и пробрасывается в QuoteModal; в браузере выполняется только `POST /api/forms/{code}` с `topic`, `source_url` и `utm` (topic берётся из пропсов/формы).
- API форм: `GET /api/forms/{code}` отдает `{ code, title, topic, submit_label, success_message, fields[] }` (fields: name/label/type/required/options), `POST /api/forms/{code}` принимает значения полей + `topic`, `source_url`, `utm` JSON; дефолтные поля email/name/message отдаются, если конфиг пуст.

- Для локального запуска соблюдайте контракт: проверяйте `./docker/compose.sh development ps`, далее `./docker/compose.sh development up --build` при необходимости.
